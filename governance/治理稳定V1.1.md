- Submission；
- 附件不可变暂存；
- Finalize；

## 3. Architecture Transition Table

| 当前主状态 | 进入条件 | 允许动作 | 成功后状态 | Fail Closed 条件 |
| --- | --- | --- | --- | --- |
| `REQUIREMENT_OBSERVED` | 正式 Issue 与初始 Projection 已存在 | 冻结 Requirement Delta | `REQUIREMENT_DELTA_FROZEN` | Issue/Project/Hash 不匹配 |
| `REQUIREMENT_DELTA_FROZEN` | Requirement Freeze Receipt 存在 | 冻结 Architecture Evidence | `ARCHITECTURE_EVIDENCE_FROZEN` | Evidence 不完整或 Hash 冲突 |
| `ARCHITECTURE_EVIDENCE_FROZEN` | Evidence 可独立读取 | 创建双盲 Assessment 槽位 | `ARCHITECTURE_ASSESSMENTS_PENDING` | 任一专家身份或 Evidence Binding 无效 |
| `ARCHITECTURE_ASSESSMENTS_PENDING` | 两个密封槽位存在 | 分别写入 Codex/ChatGPT Assessment Receipt | 保持本状态，直至双方齐备 | 一方读取另一方正文、Binding 不同或重复内容冲突 |
| `ARCHITECTURE_ASSESSMENTS_PENDING` | 双方 Receipt 齐备且绑定同一 Evidence | 解除密封并生成 Options Comparison | `OPTION_COMPARISON` | 任一 Receipt/Hash 缺失 |
| `OPTION_COMPARISON` | 比较对象冻结 | 请求 Owner 选择 | `OWNER_DECISION_REQUIRED` | Options 未冻结或比较不可读 |
| `OWNER_DECISION_REQUIRED` | Owner 明确选择一个冻结 Option | 冻结 Accepted Architecture Option | `ARCHITECTURE_OPTION_ACCEPTED` | 拒绝、暂缓、无选择或 Option Hash 不存在 |
| `ARCHITECTURE_OPTION_ACCEPTED` | Accepted Option Receipt 存在 | 形成 Consensus Proposal | `CONSENSUS_PROPOSED` | 提案偏离 Accepted Option |
| `CONSENSUS_PROPOSED` | Codex、ChatGPT 针对同一 Proposal 独立表态 | 冻结 Consensus | `CONSENSUS_REACHED` | `CHANGES_REQUESTED` 回到 `OPTION_COMPARISON`；证据不足回到 Evidence 补充分支 |
| `CONSENSUS_REACHED` | 双方同意且所有输入 Hash 齐备 | 冻结 Task Package | `TASK_PACKAGE_FROZEN` | 输入对象/合同版本/Hash 不完整 |
| `TASK_PACKAGE_FROZEN` | 允许路径、基线和测试合同固定 | Codex 实施 | `CODEX_IMPLEMENTING` | Scope、Base、路径越界 |
| `CODEX_IMPLEMENTING` | Candidate 固定 Commit/Tree 形成 | 提交 Candidate Review | `CANDIDATE_UNDER_REVIEW` | 工作树未固定或证据不完整 |
| `CANDIDATE_UNDER_REVIEW` | 三条 Verdict 轴绑定同一 Candidate | 写入独立 Verdict | 保持本状态，直至三者齐备 | 任一 Verdict 绑定不同 Candidate/Hash |
| `CANDIDATE_UNDER_REVIEW` | Codex `LOCAL_ACCEPTED`、ChatGPT `EXTERNAL_APPROVED`、Machine `PASS` 且 Open P0=0 | 单次推进 | `DUAL_APPROVED` | 任一轴缺失、失败或 P0>0 |
| `DUAL_APPROVED` | Pilot Pack 和回滚路径可用 | Pilot 数据迁移 | `PILOT_MIGRATION` | 数据证明或回滚缺失 |
| `PILOT_MIGRATION` | 迁移验证通过 | 启动观察 | `PILOT_OBSERVATION` | Hash/计数不一致 |
| `PILOT_OBSERVATION` | 观察窗口和门禁通过 | Owner 采纳 | `ARCHITECTURE_ADOPTED` | 回归、P0 或 Owner 未批准 |

补充规则：

- Assessment 是密封 Receipt，不以 Codex/ChatGPT 先后顺序创建相互覆盖的主状态。
- Candidate 记录 append-only；活动指针只能通过显式 `candidate.superseded` 从 A 指向 B。
- 轮次必须有 `round_no`、最大轮次和 Owner 决策。达到上限后进入 `OWNER_DECISION_REQUIRED`，不得无限自动循环。
- `EVIDENCE_INSUFFICIENT` 只允许形成补充请求，不得覆盖原 Evidence 或历史 Assessment。

## 4. Submission 与附件合同

### 4.1 唯一性

- `submission_id`：Primary Key/Unique。
- `formal_issue_id`：Unique。
- 同一 `submission_id` 永久绑定一个 `project_id`、一个 `capture_hash`、一个 `formal_issue_id`。

### 4.2 Capture Hash

使用带版本的 Canonical JSON，例如 `filmos.submission.capture.v1`。至少绑定：

- Project；
- 原始描述；
- Expected Result；
- Blocking；
- Context Snapshot；
- SourceIdentity 或一次性 Bootstrap Receipt；
- 按 `attachment_id` 排序的附件描述；
- 附件 SHA-256、大小、媒体类型和原始捕获时间。

排除 Attempt Time、Server Now、Retry Count、Receipt Time、Event ID 和其他运行时瞬时字段。

### 4.3 附件写入顺序

```text
临时文件完整写入
→ fsync
→ 校验大小与SHA-256
→ 原子rename到内容寻址不可变暂存区
→ BEGIN IMMEDIATE Finalize事务绑定已验证Path与Metadata
```

Finalize 事务共同写入 Submission Mapping、Formal Issue、Runtime Observation、单条 `ISSUE_CREATED`、Projection、Attachment Binding、Evidence Manifest 和 Formal Receipt。

暂存但未绑定的文件不得被 Projection、Evidence 或 MCP 读取，只能由带保留期且确认无数据库引用的 GC 清理。

## 5. Submission / Freeze Error Contract

所有外部错误只返回安全字段：`status`、`code`、`retryable`、`submission_id`、可选 `formal_issue_id`、`last_attempt_at`。不得返回 Token、数据库内容、堆栈或敏感路径。

| HTTP | Code | Retryable | 合同 |
| --- | --- | --- | --- |
| 200/201 | `SUBMISSION_ACCEPTED` | false | 首次成功或返回原 Receipt |
| 200 | `SUBMISSION_IDEMPOTENT_REPLAY` | false | 相同 submission、相同 capture hash |
| 409 | `SUBMISSION_IDEMPOTENCY_CONFLICT` | false | 相同 submission、不同 capture hash |
| 409 | `SUBMISSION_PROJECT_SCOPE_CONFLICT` | false | 草稿 Project 与投递时当前 Project 不同 |
| 409 | `ATTACHMENT_ID_CONFLICT` | false | 相同 attachment_id、不同 hash |
| 422 | `SUBMISSION_ATTACHMENT_MISSING` | false | Finalize 缺少声明附件 |
| 422 | `ATTACHMENT_INTEGRITY_FAILURE` | false | 大小或 hash 校验失败 |
| 409 | `FINALIZE_ALREADY_BOUND_CONFLICT` | false | Finalize 指向另一正式对象 |
| 503 | `INTAKE_TEMPORARILY_UNAVAILABLE` | true | 可安全重试未成功的写入 |
| 503 | `MCP_READBACK_UNAVAILABLE` | true | Receipt 已存在后只允许 GET/read 重试 |
| 409 | `READBACK_PROJECT_SCOPE_DENIED` | false | 错误 Project Grant |
| 503 | `INSTALLED_SOURCE_IDENTITY_UNAVAILABLE` | true | Stage B 后新 Intake 缺少身份 |
| 409 | `INSTALLED_SOURCE_IDENTITY_MISMATCH` | false | App 与开发仓库身份不一致 |
| 409 | `SOURCE_COMMIT_NOT_FOUND` | false | Commit 无法在开发仓库验证 |
| 409 | `SOURCE_TREE_MISMATCH` | false | Tree 不一致 |
| 409 | `APP_RUNTIME_IDENTITY_MISMATCH` | false | Bundle 与内部 Runtime 身份不一致 |
| 409 | `EVIDENCE_FROZEN_CONFLICT` | false | 已冻结 Evidence 的语义 Hash 不同 |
| 409 | `REQUIREMENT_DELTA_FROZEN_CONFLICT` | false | 已冻结 Requirement 的语义 Hash 不同 |
| 409 | `ARCHITECTURE_OPTIONS_FROZEN_CONFLICT` | false | 已冻结 Options 的语义 Hash 不同 |
| 409 | `ARCHITECTURE_OPTION_FROZEN_CONFLICT` | false | 已接受 Option 的语义 Hash 不同 |

冻结对象相同 Semantic Hash 时返回第一次原始 Freeze Receipt，`idempotent_replay=true`，不追加领域 Event、不递增版本、不改变状态。重放次数只能进入独立 Operational Audit。

## 6. Receipt、读回与 Tombstone

Receipt 成功持久化后，本地状态立即变为 `ACCEPTED_AWAITING_READBACK`，并永久停止 POST、Finalize、附件重传和 Issue 重建。

只读核验必须依次覆盖：

1. Review Bus Projection；
2. Evidence Manifest 与附件 Digest；
3. ChatGPT MCP 实际 Tool Handler；
4. 正确 Project Grant；
5. 错误 Project 被拒绝。

核对字段：`submission_id`、`formal_issue_id`、`project_id`、`capture_hash`、`receipt_hash`、`evidence_manifest_hash`。

全部核验通过后，保存不可变 Tombstone：

- `legacy_local_id`；
- `submission_id`；
- `formal_issue_id`；
- `project_id`；
- `capture_hash`；
- `receipt_hash`；
- `evidence_manifest_hash`；
- `verified_at`；
- Build Identity。

MCP 暂不可用时保留草稿与 Receipt，只重试读操作。

## 7. v2 Anchor Contract

历史 Event、Projection、Evidence、Candidate 和 Hash 不得重写。

既有 Issue 最多追加一次 `protocol.v2.anchored`，绑定：

- `legacy_last_event_hash`；
- `legacy_projection_hash`；
- `legacy_entity_version`；
- `normalized_v2_projection_hash`；
- `state_mapping_version`；
- `transition_contract_hash`；
- `migration_commit`；
- `anchored_at`。

约束：

- v1 历史前缀按旧 Hash Chain 验证；
- v2 语义链只从 Anchor 后验证；
- 旧链失败时禁止 Anchor；
- 验收只能声明 `LEGACY_HASH_CHAIN_VALID` 和 `V2_SEMANTIC_CHAIN_VALID_FROM_ANCHOR`；
- 不得声明 `FULL_HISTORY_SEMANTIC_PASS`；
- v2 新 Issue 从 v2 Genesis 开始，不创建 Legacy Anchor；
- Projection Semantic Hash 必须排除自身 Hash、Event Hash 等自引用字段。

Stage A 完成后，新的 Intake 入口保持关闭，直到 Stage B 完成 Installed SourceIdentity 并验证 Bundle、Runtime、Commit、Tree、Source Fingerprint、Repository 和开发仓库真实 Git 对象。

## 10. 阶段 Commit 边界

Stage A 推荐拆分为可审计小提交：

1. `fix(review-intake): Submission - 固定唯一性与规范化Hash`
2. `fix(review-intake): Attachment - 增加不可变暂存与完整性验证`
3. `fix(review-intake): Finalize - 原子绑定Issue和Receipt`
4. `fix(review-intake): Migration - 恢复旧草稿并完成只读核验`
5. `test(review-intake): Recovery - 覆盖幂等并发和崩溃恢复`

Stage B 推荐独立提交：

1. Transition Contract；
2. Freeze/Owner Gate；
3. Assessment/Consensus/Candidate Binding；
4. Coordinator Recovery；
5. v2 Anchor/SourceIdentity；
6. 测试与 Canary。

Stage C1 和 C2 必须分别提交。C2 Cleanup Commit 只能包含清理及生成规则，不能包含业务修复。

Stage A 开始前，暂停补丁必须逐文件标注 `REUSE`、`REWORK`、`DROP`、`UNRELATED`。任何复用内容都必须重新应用到新的独立 Stage A worktree，并重新验证；不得把暂停 worktree 直接推进为 Candidate。
